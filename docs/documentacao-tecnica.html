1. Visão Geral do Sistema

O sistema de busca de teses jurídicas trabalhistas é uma aplicação de inteligência artificial aplicada ao Direito do Trabalho. O objetivo central é simples: um advogado descreve o argumento da parte contrária que precisa rebater, e o sistema localiza automaticamente nos documentos do acervo os trechos mais relevantes, gerando uma análise estratégica dos argumentos a utilizar.

Para isso, o sistema combina três grandes tecnologias modernas de IA:

  • Busca semântica vetorial — em vez de buscar palavras-chave exatas, o sistema entende o significado da consulta e encontra trechos semanticamente relacionados, mesmo que usem vocabulário diferente.
  • Large Language Models (LLM) — o modelo GPT-4o da OpenAI lê os trechos encontrados e gera uma análise consolidada, indicando quais argumentos são mais fortes e como utilizá-los.
  • RAG (Retrieval Augmented Generation) — padrão arquitetural que combina busca em base de conhecimento própria com geração de texto pela IA, garantindo que as respostas sejam fundamentadas em documentos reais do escritório.
Por que RAG e não um chatbot comum? Um chatbot comum (como o ChatGPT sem personalização) só conhece o que foi treinado. O sistema RAG alimenta a IA com os documentos reais do seu escritório no momento da consulta. Isso significa que as respostas são baseadas nas suas teses específicas, não em conhecimento genérico da internet.

2. O que é RAG (Retrieval Augmented Generation)

RAG é o padrão arquitetural mais adotado atualmente para construir sistemas de IA sobre bases de conhecimento privadas. O nome traduz exatamente o que acontece:

  • Retrieval (Recuperação): busca os documentos mais relevantes na base
  • Augmented (Aumentado): aumenta o contexto enviado para a IA com esses documentos
  • Generation (Geração): a IA gera a resposta usando esse contexto como base

O problema que o RAG resolve

Modelos de linguagem como o GPT-4o são treinados com dados públicos até uma data de corte. Eles não conhecem:

  • As teses específicas do seu escritório
  • Documentos confidenciais ou internos
  • Argumentos construídos pela sua equipe ao longo dos anos

Com RAG, esses documentos são incluídos dinamicamente em cada consulta. A IA recebe: "Aqui estão os 8 trechos mais relevantes do acervo. Agora analise e responda."

Fluxo conceitual do RAG

FASE 1 — INDEXAÇÃO (feita uma vez, ou quando documentos mudam) Documento PDF/DOCX │ ▼ Extração de Texto │ ▼ Divisão em Chunks (pedaços menores) │ ▼ Geração de Embeddings (vetor numérico que representa o significado) │ ▼ Armazenamento no Banco Vetorial (Supabase pgvector) FASE 2 — CONSULTA (em tempo real, a cada busca) Pergunta do Advogado │ ▼ Geração do Embedding da Pergunta │ ▼ Busca por Similaridade no Banco Vetorial (encontra os chunks mais próximos semanticamente) │ ▼ Os N chunks mais relevantes são enviados ao GPT-4o │ ▼ GPT-4o gera análise estratégica baseada nesses documentos │ ▼ Resposta para o Advogado (análise + documentos com links)

4. Pipeline de Indexação

A indexação é o processo de preparar os documentos para que possam ser buscados. É feita chamando POST /api/index e pode ser repetida quando novos documentos são adicionados ao Drive. O sistema é inteligente: não reindexia arquivos que não foram modificados, economizando tempo e custo de API.

POST /api/index │ ▼ 1. Listar arquivos no Google Drive (recursivo em subpastas) │ ├─── Para cada arquivo: │ │ │ ▼ │ 2. Verificar se o arquivo mudou desde a última indexação │ │ (comparando modifiedTime com o valor salvo no Supabase) │ │ │ ├── Não mudou → IGNORAR (status: "ignorado") │ │ │ └── Mudou ou novo: │ │ │ ▼ │ 3. Extrair texto do arquivo │ (.pdf → PyMuPDF | .docx → python-docx | Google Doc → export) │ │ │ ▼ │ 4. Dividir em chunks jurídicos │ (respeitando seções: EMENTA, FUNDAMENTAÇÃO, etc.) │ │ │ ▼ │ 5. Gerar embeddings em batch via OpenAI │ (um vetor de 1536 dimensões por chunk) │ │ │ ▼ │ 6. Deletar chunks antigos (se reindexando) │ │ │ ▼ │ 7. Salvar novos chunks no Supabase │ (texto + embedding + metadados) │ ▼ Retorna relatório: indexados / atualizados / ignorados / erros

Controle de versão dos documentos

Cada arquivo no Google Drive possui um campo modifiedTime (data/hora da última modificação). O sistema salva esse valor junto com o chunk no Supabase. Na próxima indexação, compara o valor atual do Drive com o salvo — se forem iguais, o arquivo não mudou e é pulado. Se mudou, os chunks antigos são deletados e o arquivo é reprocessado do zero.

Custo de reindexação Cada chamada à API de embeddings da OpenAI tem um custo. O controle de versão garante que só arquivos modificados ou novos geram custo. Para um acervo de 100 documentos onde apenas 5 foram alterados, o custo é de apenas 5 arquivos.

6. Google Drive — Integração e Extração de Texto

O Google Drive funciona como o repositório central dos documentos. A integração usa uma Service Account — uma conta de serviço do Google Cloud que permite ao backend acessar o Drive programaticamente, sem precisar de login manual.

Como funciona a autenticação

O Google Cloud fornece um arquivo JSON com uma chave privada RSA para a service account. O backend usa esse JSON para se autenticar e receber um token de acesso temporário. Em produção (Render.com), o conteúdo JSON é armazenado como variável de ambiente para evitar arquivos físicos no servidor.

O código detecta automaticamente se o valor em GOOGLE_SERVICE_ACCOUNT_JSON começa com { (JSON inline, usado em produção) ou é um caminho de arquivo (usado localmente):

def _get_drive_service():
    value = settings.GOOGLE_SERVICE_ACCOUNT_JSON.strip()
    if value.startswith("{"):
        # Produção: JSON inline como variável de ambiente
        info = json.loads(value)
        creds = service_account.Credentials.from_service_account_info(info, scopes=SCOPES)
    else:
        # Local: caminho para o arquivo JSON
        creds = service_account.Credentials.from_service_account_file(value, scopes=SCOPES)
    return build("drive", "v3", credentials=creds, cache_discovery=False)

Listagem recursiva de subpastas

O sistema percorre todas as subpastas recursivamente a partir de uma pasta raiz configurada. Isso significa que a estrutura de organização do Drive pode ser tão aninhada quanto necessário — o sistema encontrará todos os documentos:

def _listar_recursivo(service, folder_id, resultado):

7. Chunking Jurídico — Divisão Inteligente de Texto

Um problema fundamental de RAG é que modelos de linguagem têm um limite de contexto — não é possível enviar um documento inteiro de 50 páginas. A solução é dividir os documentos em pedaços menores chamados chunks, que são armazenados e buscados individualmente.

A divisão ingênua (ex: a cada 1000 caracteres) quebraria argumentos jurídicos no meio de uma fundamentação. O sistema usa uma estratégia em três camadas:

Camada 1 — Divisão por seções jurídicas

O chunking identifica marcadores de seções jurídicas comuns nos documentos e usa-os como fronteiras naturais. As seções reconhecidas incluem:

EMENTA, ACÓRDÃO, RELATÓRIO, FUNDAMENTAÇÃO, FUNDAMENTOS,
DISPOSITIVO, CONCLUSÃO, DOS FATOS, DO DIREITO, DO PEDIDO,
PEDIDO, TESE, numerações romanas (I –, II –, III –),
títulos numerados (1. RESCISÃO INDIRETA, 2. HORAS EXTRAS...)

Camada 2 — Subdivisão por parágrafos

Se uma seção for muito grande (superar o limite de tokens configurado), ela é subdividida por parágrafos. O limite padrão é de 800 tokens por chunk (aproximadamente 600 palavras).

Camada 3 — Overlap entre chunks

Para evitar que um argumento que cruza a fronteira entre dois chunks seja perdido, o sistema aplica um overlap de 100 tokens: o início de cada novo chunk repete o final do chunk anterior. Isso garante que o contexto seja preservado nas bordas.

Por que 800 tokens e não mais? Chunks maiores carregam mais contexto, mas reduzem a precisão da busca semântica (o embedding representa um texto mais "médio" e menos específico). Chunks menores são mais precisos, mas podem perder contexto. 800 tokens é o equilíbrio encontrado para documentos jurídicos longos.

Estimativa de tokens

O sistema usa uma estimativa simplificada de 1 token ≈ 4 caracteres. Essa heurística funciona bem para textos em português, onde a maioria das palavras tem entre 1 e 2 tokens no tokenizador da OpenAI.

8. Embeddings — Representação Vetorial do Texto

Um embedding é a representação numérica do significado de um texto. É um vetor (lista) de números de ponto flutuante, onde textos semanticamente similares produzem vetores matematicamente próximos.

Como um embedding captura significado

Considere três frases:

  • "O empregado foi demitido sem justa causa"
  • "O trabalhador teve seu contrato encerrado sem motivo"
  • "O preço do café subiu esta semana"

As duas primeiras, apesar de usarem palavras diferentes, ficam muito próximas no espaço vetorial. A terceira fica distante. É assim que a busca semântica encontra resultados relevantes mesmo que o advogado use vocabulário diferente do documento.

O modelo usado: text-embedding-3-small

PropriedadeValor
Modelotext-embedding-3-small (OpenAI)

Custo~$0,02 por 1 milhão de tokens

Geração em batch para eficiência

Ao indexar um documento com muitos chunks, o sistema agrupa todos em uma única chamada à API (batch), reduzindo o número de requisições e o tempo total:

async def gerar_embeddings_batch(textos: List[str]) -> List[List[float]]:
    response = await client.embeddings.create(
        model="text-embedding-3-small",
        input=textos  # envia todos os chunks de uma vez
    )
    return [item.embedding for item in response.data]

9. Supabase e pgvector — Banco Vetorial

O Supabase é um banco de dados PostgreSQL gerenciado com funcionalidades adicionais (autenticação, storage, realtime). Para este sistema, usa-se o pgvector, extensão do PostgreSQL que adiciona suporte nativo a vetores e busca por similaridade.

Por que Supabase e não um banco vetorial dedicado (Pinecone, Weaviate)?

Bancos vetoriais dedicados são otimizados para escala massiva. Para um acervo jurídico de até alguns milhares de documentos, o pgvector no Supabase oferece performance excelente com muito menos complexidade operacional — e com plano gratuito generoso.

Estrutura da tabela

CREATE TABLE teses (
    id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    arquivo_nome          TEXT NOT NULL,         -- nome do arquivo no Drive
    arquivo_id            TEXT NOT NULL,         -- ID único no Google Drive
    arquivo_link          TEXT,                  -- URL para abrir no Drive
    arquivo_modified_time TEXT,                  -- data de modificação (controle de versão)
    chunk_index           INTEGER NOT NULL,      -- posição do chunk no arquivo (0, 1, 2...)
    conteudo              TEXT NOT NULL,         -- o texto do chunk
    embedding             VECTOR(1536),          -- o vetor de 1536 dimensões
    pagina                INTEGER,               -- página do PDF (quando disponível)
    created_at            TIMESTAMPTZ DEFAULT now()
);

Índice vetorial IVFFlat

Para busca eficiente em grandes volumes de vetores, o sistema cria um índice do tipo IVFFlat (Inverted File with Flat Compression):

CREATE INDEX teses_embedding_idx
    ON teses USING ivfflat (embedding vector_cosine_ops)
    WITH (lists = 100);

O parâmetro lists = 100 divide o espaço vetorial em 100 clusters. Na busca, o PostgreSQL só compara com vetores do cluster mais próximo, tornando a busca muito mais rápida que comparar com todos os vetores. O valor ideal de lists é aproximadamente √N onde N é o número esperado de registros.

Similaridade coseno

A medida de proximidade usada é a similaridade coseno, que mede o ângulo entre dois vetores (e não a distância euclidiana). Isso é preferível para embeddings porque o comprimento do vetor não importa — só a direção, que representa o significado.

  • Similaridade = 1.0 → textos idênticos em significado
  • Similaridade = 0.8+ → muito relevante
  • Similaridade = 0.5–0.8 → moderadamente relevante
  • Similaridade = abaixo de 0.3 → descartado pelo threshold

O operador <=> no pgvector calcula a distância coseno (1 - similaridade). Por isso, a função SQL usa 1 - (embedding <=> query_embedding) para obter a similaridade:

CREATE OR REPLACE FUNCTION match_teses(
    query_embedding   VECTOR(1536),
    match_count       INT     DEFAULT 8,
    match_threshold   FLOAT   DEFAULT 0.3
)
RETURNS TABLE (id UUID, arquivo_nome TEXT, conteudo TEXT, similarity FLOAT, ...)
AS $$
BEGIN
    RETURN QUERY
    SELECT
        t.id, t.arquivo_nome, t.conteudo,
        1 - (t.embedding <=> query_embedding) AS similarity  -- similaridade coseno
    FROM teses t
    WHERE 1 - (t.embedding <=> query_embedding) > match_threshold  -- filtro de threshold
    ORDER BY t.embedding <=> query_embedding  -- mais próximo primeiro
    LIMIT match_count;
END;
$$;

Row Level Security (RLS)

A tabela tem RLS habilitado. O backend usa a service_role key do Supabase, que bypassa o RLS automaticamente — isso garante acesso completo para o backend enquanto impede acesso não autorizado por outras vias.

10. FastAPI — Backend e Endpoints

O FastAPI é um framework Python moderno para construção de APIs, com suporte nativo a programação assíncrona (async/await), tipagem via Pydantic e documentação automática. É um dos frameworks mais rápidos disponíveis para Python.

Configuração de CORS

CORS (Cross-Origin Resource Sharing) é o mecanismo de segurança do browser que controla quais origens podem fazer chamadas à API. O backend configura as origens permitidas via variável de ambiente:

app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.ALLOWED_ORIGINS,  # ["https://seu-site.netlify.app"]
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

Modelos de dados com Pydantic

Todos os contratos de entrada e saída da API são definidos como modelos Pydantic, que fazem validação automática, serialização e geração de documentação OpenAPI:

A indexação de muitos documentos pode levar vários minutos. Para evitar que duas indexações rodem ao mesmo tempo (o que causaria duplicação de dados), o sistema usa uma flag simples:

    _indexando = True
    resultado = await _executar_indexacao(...)
    _indexando = False
    return resultado

11. OpenAI GPT-4o — Análise por IA

Após a busca vetorial retornar os chunks mais relevantes, eles são enviados ao GPT-4o para análise. O modelo recebe dois tipos de instruções:

System Prompt (instrução de papel)

Define o comportamento e especialização do modelo para todas as interações:

"Você é um assistente jurídico especializado em Direito do Trabalho brasileiro.
Sua função é analisar teses jurídicas encontradas em uma base de documentos e ajudar
advogados a identificar os melhores argumentos para rebater ações trabalhistas.
Sempre responda em português brasileiro de forma técnica, clara e objetiva.
Use terminologia jurídica adequada."

User Prompt (instrução por consulta)

Inclui a consulta do advogado e os documentos encontrados. O modelo recebe instruções específicas de análise:

  1. Identificar as teses mais relevantes para o caso
  2. Explicar como cada tese pode ser usada para rebater o argumento
  3. Sugerir a ordem de apresentação (do argumento mais forte ao mais fraco)
  4. Apontar jurisprudências e fundamentos legais mencionados

12. Frontend — Next.js + Tailwind CSS

O frontend é construído com Next.js 16 (App Router) e Tailwind CSS 4, hospedado no Netlify. A interface foi projetada para advogados: limpa, profissional e focada na tarefa.

Separação Server / Client Components

O Next.js App Router distingue dois tipos de componentes:

  • Server Components (padrão): renderizados no servidor, sem JavaScript enviado ao cliente. Usados para o layout, cabeçalho e página principal.
  • Client Components (marcados com "use client"): têm acesso a estado, eventos e APIs do browser. Usado para o formulário de busca e exibição de resultados.

Cliente HTTP

As chamadas ao backend são feitas via fetch nativo, com tratamento de erros:

export async function searchTeses(payload: SearchRequest): Promise<SearchResponse> {
  const res = await fetch(`${API_URL}/api/search`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(payload),
  });
  if (!res.ok) {
    const data = await res.json();
    throw new Error(data?.detail ?? `Erro ${res.status}`);
  }
  return res.json();
}

Skeleton de loading

Enquanto a resposta do backend é aguardada (normalmente 5–15 segundos, considerando embedding + busca + GPT-4o), o frontend exibe um skeleton animado que replica o layout da resposta real, evitando a percepção de "tela travada".

Deploy contínuo

Ambos Render e Netlify monitoram o repositório GitHub. Qualquer git push na branch main dispara um novo deploy automático. O processo completo leva cerca de 1–2 minutos (após o primeiro, que é mais lento por falta de cache).

Cold Start no Render (plano gratuito)

No plano gratuito do Render, o servidor hiberna após 15 minutos sem tráfego. A primeira requisição após o período de hibernação acorda o servidor, o que pode levar 20–30 segundos. As requisições subsequentes são normais. Para uso interno em escritório, isso costuma ser aceitável.

Configuração Python no Render

O arquivo .python-version na raiz do backend fixa a versão do Python em 3.12. Isso é necessário porque versões mais recentes do Python (3.13+) ainda não possuem wheels pré-compilados para todas as dependências, o que causaria falha no build.

14. Segurança

O que está protegido

  • .env e credentials/ estão no .gitignore e nunca são commitados
  • Service keys ficam apenas nas variáveis de ambiente dos serviços de hospedagem (criptografadas em repouso)
  • CORS restringe chamadas ao backend apenas para origens autorizadas
  • RLS no Supabase impede acesso direto ao banco via chave pública
  • NEXT_PUBLIC_ no frontend: apenas a URL do backend é exposta no cliente (não há credenciais)

O que ainda pode ser melhorado

  • Adicionar autenticação no backend (Basic Auth ou JWT) para proteger os endpoints de acesso não autorizado — atualmente qualquer pessoa com a URL do Render pode chamar a API
  • Rate limiting para evitar uso excessivo e custos inesperados na OpenAI
  • Logs de auditoria das consultas realizadas
Atenção às chaves da OpenAI A chave da OpenAI tem acesso de faturamento direto. Configure limites de gasto mensais no painel da OpenAI (Settings → Limits) para evitar custos inesperados em caso de uso indevido.
